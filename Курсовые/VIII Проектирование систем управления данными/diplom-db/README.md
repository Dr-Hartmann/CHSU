## Запрос на создание клиента

Клиентское приложение для базы данных. База данных уже есть, API представляет собой CRUD-операции. Сущности БД: 

```sql
/* 
 * ИИ-сценарист -- в регламенте описание устройства: надо создать инструкцию. 
 * Скрытые смыслы модель должна понять сама.
 * Пример
 * Включить утюг У-505: (сценарий)
 * 0.1  Проверить что вилка есть (да)
 * 1.   Взять вилку А-101; (ID1, name) : 1 - правильно, но требует корректировки
 * 1.1. Попить чай : 2 - правильно, но не своём месте
 * 1.2. Покричать на небо : 3 - неправильно и не на своём месте
 * 2.   Воткнуть в розетку B-202; (ID2, name) : 4 - правильно и на своём месте
 * 2.3. ...
 * 3.   Нажать включить кнопку C-304. (ID3, name)
*/

-- Объект, над которым будет действие (заполняет LLM)
Table objects {
  ~base
  name varchar [note: 'Алиас из регламента']
  Records {
    1, '2026-11-11', '2026-11-11', "вилка А-101"
    2, '2026-11-11', '2026-11-11', "вилка А-102"
    3, '2026-11-11', '2026-11-11', "кнопка B-301"
  }
}

-- Действие (заполняет LLM)
Table actions {
  ~base
  name varchar [note: 'Название единицы действия']
  Records {
    1, '2026-11-11', '2026-11-11', "взять"
    2, '2026-11-11', '2026-11-11', "вставить"
    3, '2026-11-11', '2026-11-11', "нажать"
  }
}

-- Шаги (заполняет LLM)
-- ! база данных разрастётся = проблемы в будущем (надо как то чистить?)
Table steps {
  ~base
  action_id guid [ref: > actions.id, not null]
  object_id guid [ref: > objects.id, not null]
  Records {
    1, '2026-11-11', '2026-11-11', 1, 1
    2, '2026-11-11', '2026-11-11', 2, 1
    3, '2026-11-11', '2026-11-11', 3, 3
  }
}

-- Сценарии_шаги (многие-ко-многим, заполняет LLM)
Table scenarios_steps {
  ~base
  scenario_id guid [ref: > scenarios.id, not null]
  step_id guid [ref: > steps.id, not null]
  order int [note: 'Порядок шага в сценарии']
  Records {
    1, '2026-11-11', '2026-11-11', 1, 1, 1
    2, '2026-11-11', '2026-11-11', 1, 2, 2
    3, '2026-11-11', '2026-11-11', 1, 3, 3
  }
}

/*
 * Для вводимых пользователем файлов нужно использовать S3-совместимое хранилище, в чате хранить ссылку/id на него.
 * В случае с документами, которые были в файловом хранилище при создании эмбеддингов, используются "парсеры",
 * которые извлекают смысл из содержимого документа, это превращается в чанки и отправляется в векторную БД.
*/

-- Сценарии (заполняет LLM)
Table scenarios {
  ~base
  parent_scenario_id guid [ref: > scenarios.id] [note: 'Может быть null, если корень.']
  user_request text [note: 'Запрос пользователя + чанки эмбеддингов и ссылки на файлы']
  llm_context json [note: 'Ответ LLM']
  child_count int [note: 'Число обратных ссылок; для удаления']
  Records {
    1, '2026-11-11', '2026-11-11', null, "...", "...", 1
  }
}

/*
 * Если два человека зашли в одну уже существующую сессию, то каждый создаст свой запрос,
 * и к последнему запросу будут ссылаться два разных запроса.
*/

-- Пользовательские сессии: ссылка на ноду/лист в дереве/коммит запроса (типо HEAD в Git).
Table sessions {
  ~base
  scenario_id guid [ref: - scenarios.id, not null]
  course_name varchar [note: 'Название курса']
  Records {
    1, '2026-11-11', '2026-11-11', 1, "..."
  }
}

-- Шаблон базовых полей
TablePartial base {
  id guid [pk]
  created_at timestamp [default: `now()`]
  updated_at timestamp [default: `now()`]
  is_deleted boolean [default: false] [note: 'Для мягкого удаления']
}
```

Клиентское приложение должно отражать таблицы БД в удобном табличном виде, причем ID внешних ключей заменены на их значения имени/какого то поля из своей основной таблицы. Приложение представляет собой черно белый (типо WinForms) однооконный менеджер БД. Тип СУБД - PostgreSQL. Нет авторизации и аутентификации, но есть возможность смены строки подключения в этом же окне. Выбор таблиц идёт из выпадающего списка. Выбор некоторых значений в полях при создании/редактировании сущностей идёт из выпадающего списка (имена вместо ID).
